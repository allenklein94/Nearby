### 1b. A real, concrete, currently-live reproducibility bug — found by inspection, not assumed

**`supabase/migrations/20260809_social_invite_community_join.sql` will fail to replay against
`00000000000000_baseline.sql` with a `policy already exists` error.**

This file's own header comment describes it as the Leg-4 flywheel-trace fix: it does
`drop policy if exists "Users can join public communities, or their own community regar" ...`
(the *old*, pre-fix policy name) and then
`create policy "Users can join public communities, invited communities, or thei" ...` (the
*new*, fixed policy, adding a third `social_invites`-based INSERT path).

The problem: **the baseline file was regenerated at a point in time *after* this fix was already
live in production**, so the baseline's own `CREATE TABLE`/`CREATE POLICY` section for
`community_members` **already contains this exact new policy, under this exact name**:

```
grep -n 'Users can join public communities, invited communities, or thei' migrations/00000000000000_baseline.sql
5197:create policy "Users can join public communities, invited communities, or thei"
```

So replaying the committed files in filename order (`00000000000000_baseline.sql` →
`20260809_business_customer_notes.sql` → `20260809_business_profile_self_edit.sql` →
`20260809_social_invite_community_join.sql`) means: baseline creates the policy once, then the
fourth file's `drop policy if exists <old name>` is a harmless no-op (that name was never
created), and then its `create policy "Users can join public communities, invited communities,
or thei" ...` **collides with the identical policy name the baseline already created**. Postgres'
`CREATE POLICY` has no `IF NOT EXISTS`/`OR REPLACE` form — this is a hard, deterministic
`ERROR: policy "..." for table "community_members" already exists`, not a maybe.

I confirmed this three ways, not just by reading the two files side by side:
1. `grep -c` for the exact new policy name inside a name-list extracted from
   `20260809_business_customer_notes.sql` + baseline (`baseline_policy_names.txt`) returned `1`
   — i.e. the name is already present before the fourth file even runs.
2. Live `pg_policies` confirms this exact policy is the one *actually deployed right now* on
   `community_members` (verified in section 2 below) — so the baseline's copy is not stale/wrong,
   it's the live, current, correct state, just already-baked-in.
3. The other two files sitting alongside it in `supabase/migrations/`
   (`business_customer_notes.sql`, `business_profile_self_edit.sql`) create genuinely *new*
   objects (a table that doesn't exist in baseline, functions that don't exist in baseline) —
   confirmed via the same grep-diff technique in 1a — so those two are correctly-shaped real
   incremental migrations. `social_invite_community_join.sql` is the only one of the three that
   is not: it's a **redundant leftover** that should have been archived (its effect is already
   permanently captured in the baseline) but was not, and it will break a from-scratch replay if
   left where it is.

**This is a materially different, and narrower, situation than CLAUDE.md's "Aug 9 2026 — schema
baseline fix" section believes it left things.** That section's own rigorous Docker
empty-database test proved **the baseline file alone** applies cleanly — true, re-confirmed by
the table/function name diffs in 1a above. But that Docker test necessarily predates
`business_profile_self_edit.sql` and `business_customer_notes.sql` (both created ~48–51 minutes
*after* the baseline file's own mtime, per `ls -la` timestamps: baseline 18:00, those two files
18:48/18:51) and it never re-tested "baseline + whatever is currently sitting in
`supabase/migrations/`" as a combined unit — only the baseline in isolation. The
`social_invite_community_join.sql` file (mtime 17:57, *before* the baseline was cut, so its
effect really was already inside the baseline pull) was apparently never moved to
`migrations_archive/` the way its three Aug-9 siblings
(`join_gathering_invite_only_check.sql`, `momentum_reward_nudges.sql`,
`offer_redemption_proof.sql`) correctly were.

**Verdict for section 1: PARTIAL, not YES.** A fresh empty Supabase project loaded with
`00000000000000_baseline.sql` alone reproduces the schema that existed at ~18:00 today
(re-confirmed structurally sound in this pass). But **replaying the full, current
`supabase/migrations/` folder in order — which is what "this repo can rebuild itself from
committed files" has to mean once there are migrations layered on a baseline — hits a real,
reproducible `policy already exists` error on the third file**, before ever reaching
`business_profile_self_edit.sql`'s and `business_customer_notes.sql`'s genuinely-new objects
(both of which I confirmed, independently, WOULD apply cleanly if reached — no naming conflicts,
all their dependencies, e.g. `profiles`, `brand_partners`, already exist in baseline).

**Fix required** (not performed — this is a read-only research pass, no application/schema
files were touched): delete `supabase/migrations/20260809_social_invite_community_join.sql` (or
move it to `migrations_archive/`, matching its three same-day siblings) since its effect is
already permanently inside the baseline and the file only exists to break a clean replay now.

### A real gap identified by re-reading the old audit's own open question, checked live and found already closed (a **correction to `PRODUCT_AUDIT`**, not a new finding)

`business_partnership_requests`' Part-1 design plan (CLAUDE.md, "Create Consolidation" section)
explicitly flagged, as a to-check-before-building item: *"check live whether gatherings/
communities' existing owner-scoped UPDATE RLS already lets a host self-set their own
hosting_partner_id to an arbitrary partner id with no consent check."* I could not find anywhere
in CLAUDE.md's later "DONE" status write-up for that section confirming this was actually
checked or fixed — it reads like an open question the plan raised and then never circled back to
narrate the answer for. So I tested it live, on a real (non-test) gathering, rather than assuming
either "yes it was fixed" or "no it wasn't":

- `gatherings`' live UPDATE policy: `qual`/`with_check` both just `host_id = auth.uid()` — **no
  column-level restriction in the RLS policy itself.** Taken alone, this would mean a host could
  set `hosting_partner_id` to any real partner id with zero consent from that business.
- **Live test**: as the real host (`Claude`) of a real, pre-existing, non-test gathering
  (`9a523429-...`, `hosting_partner_id` confirmed `null` beforehand), attempted
  `update gatherings set hosting_partner_id = '<Coastal Coffee's real id>' where id = <own
  gathering> returning id, hosting_partner_id` — the `RETURNING` clause came back
  `hosting_partner_id: null`, i.e. **silently reverted**, not applied. Re-confirmed as `postgres`
  immediately after: still `null`. Nothing was left changed on this real, non-test row.
- Root cause found: a `BEFORE UPDATE` trigger on both `gatherings` and `communities`
  (`on_gathering_updated_protect_partner` / `on_community_updated_protect_partner`, both calling
  the same `prevent_hosting_partner_self_edit()` function) reverts `hosting_partner_id` to its
  old value unless `app.trusted_update` is set — the exact same guarded-column pattern as
  `prevent_self_premium_edit()`. Confirmed this trigger is present on both tables in the live
  catalog, confirmed its function body, and confirmed it's the same escape hatch
  `respond_to_business_partnership_request()`'s own live source legitimately uses
  (`perform set_config('app.trusted_update', 'true', true);` right before it writes
  `hosting_partner_id` on approval) — so the legitimate approval path still works, only a raw
  client self-edit is blocked.
- **Classification: CONFIRMED SECURE.** This closes an open question CLAUDE.md's own plan raised
