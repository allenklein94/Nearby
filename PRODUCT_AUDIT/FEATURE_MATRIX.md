# Feature Matrix — Nearby

*Basis: `SCREEN_INVENTORY.md`, `DATABASE_AND_DATA_MODEL.md`, `NAVIGATION_AND_IA.md`, and direct
greps of `src/services/`. "Complete?" reflects what was directly observed working end-to-end in
the client code reviewed — it does not certify production behavior that couldn't be checked
from this repo alone (e.g. live Anthropic calls, real device push delivery). Where evidence was
thin, the row says so explicitly rather than assuming.*

| Feature | Exists? | Complete? | Where implemented | Notes |
|---|---|---|---|---|
| Authentication | Yes | Yes | `LoginScreen.js`, Supabase Auth (phone OTP) | Includes a hardcoded App-Review reviewer-phone bypass calling a raw `fetch()` to a hardcoded Edge Function URL/key — works, but an inconsistent implementation pattern (see `IMPLEMENTATION_NOTES.md`). |
| Onboarding | Yes | Partial | `Onboarding`→`OnboardingQuestions`→`OnboardingLocation`→`Login`→`CompleteProfile`→`OnboardingRecommendations` | The location-preference answer is collected but never used downstream; the post-signup recommendation cards all navigate identically regardless of which one is tapped (confirmed bug). |
| Profiles | Yes | Yes | `ProfileScreen.js`, `ViewProfileScreen.js`, `profiles` table | Rich: photos, prompts, interests, connection goals, host reputation, mutual friends, compatibility scoring. |
| Discover (unified hub) | Yes | Yes | `DiscoverHubScreen.js` | Search+filter+map/list across gatherings/communities/places/perks; People deliberately excluded (anti-stalking design choice). |
| Search | Yes | Partial | client-side filter in `DiscoverHubScreen.js` over already-fetched gathering/community/perk lists; live Google Places query for Places | Not a real backend full-text search — a client-side substring filter over whatever's already loaded, so results are bounded by however much was originally fetched. |
| Gatherings | Yes | Yes | `GatheringsScreen.js`, `GatheringDetailScreen.js`, `GatheringHubScreen.js`, `gatherings`/`gathering_interest` tables | Very deep: capacity/waitlist, visibility scoping, vibe fields, Q&A, live hub, feedback loop, host reputation. |
| Communities | Yes | Yes | `CommunitiesScreen.js`, `CommunityDetailScreen.js`, `community_members` | Roles (creator/leader/member), calendar view, business affiliation. |
| Create (unified flow) | Yes | Yes | `CreateHubScreen.js`, `CreateGatheringScreen.js`, `create-assistant` Edge Function | One-decision-per-screen wizard; free-text AI classification for the catch-all path. |
| Invitations | Yes | Partial | `social_invites` table, `InviteFriendsModal.js`, `Inbox` Invites tab | Real and friends-only-gated for gatherings/communities, but this is a **different mechanism** from the separate app-referral "invite" screen — the shared word covers two unrelated systems (see `USER_FLOWS.md` flow E). |
| Connections (friends) | Yes | Yes | `FriendsScreen.js`, `friendships` table, `friend_circles` | Includes contacts-import matching and custom "Circles" grouping. |
| Messaging (1:1) | Yes | Partial | `ChatScreen.js`, `messages` table | Feature-rich (voice/photo/video/GIF/translation/disappearing messages), but ships a production debug overlay on every message bubble (confirmed bug) and silently drops a message on a failed send. |
| Group chats | Yes | Partial | `GatheringChatScreen.js`, `CommunityChatScreen.js` | Same silent-send-failure pattern as 1:1 chat. |
| Activity | Yes | Yes | `ActivityScreen.js` (registered as the `Notices` route) | Unified notices/sightings/friend-request/business-update feed. A separate, superseded `NoticesScreen.js` file is fully dead code. |
| Notifications | Yes | Partial | `services/notifications.js`, `send-push` Edge Function | Push routing logic for match/message/friend/gathering-invite/reminder types is correctly wired client-side per `CLAUDE.md`'s own audit trail, but whether every server-side trigger that's *supposed* to send a push actually fires in production (e.g. `gathering_reminder`) was flagged in that same history as never independently re-verified — treat as UNCLEAR beyond the client-side routing logic itself. |
| Business profiles | Yes | Yes | `BusinessProfileScreen.js`, `brand_partners` table | Public-facing, real follower/reputation/perks/gatherings data, no fabricated fields. |
| Business mode | Yes | Yes (as a concept), but thin as a "mode" | `profiles.managed_partner_id` conditional UI in `ProfileScreen.js`/`SettingsScreen.js` | Not a real app-shell mode switch — same 5 tabs for everyone, just a conditional dashboard link in two places (duplicated gating logic). No persistent "you're in business mode" indicator. |
| Business dashboard | Yes | Partial | `BusinessDashboardScreen.js` | Deep analytics/CRM (growth, attendee breakdown, top-member drill-in, insights) genuinely built — but the dashboard's own "Business" tab admits editing the business's own name/description/logo isn't implemented yet. |
| Business partnerships | Yes | Yes | `RequestBusinessPartnerScreen.js`, `BusinessPartnerApplyScreen.js`, `business_partnership_requests`/`business_partner_requests` | Two similarly-named, separate flows — a generic "become a partner" application vs. a specific gathering/community sponsorship request — both real and working, but a real terminology-overlap risk for users and future maintainers. |
| Perks/rewards | Yes | Yes | `BrandOffersScreen.js`, `RewardsScreen.js`, `brand_offers`, `offer_redemptions` | Scarcity, targeting, group-unlock thresholds (server-enforced), redemption-based loyalty tiers. `RewardsScreen` itself is a dead-end (no CTA to go redeem). |
| Redemption | Yes | Partial | `redeemOffer()` in `services/brandOffers.js` | Records a redemption server-side with real limit/unlock enforcement, but **no in-app proof-of-redemption mechanism (QR/code/staff confirmation) was found** — how a business confirms a redemption happened in person is UNCLEAR from the code. |
| Billing (business side) | Yes | Partial | `partner_contracts`, `business_invoices`, monthly `pg_cron` invoice generator | Real usage-based billing math runs and writes real invoice rows on schedule, per `CLAUDE.md` — but invoices sit in `draft` forever; **no payment processor is integrated at all**. Money never actually moves. |
| Payments (consumer subscription) | Yes | Yes | `PaywallScreen.js`, `BillingScreen.js`, RevenueCat (`react-native-purchases`) | Real native in-app-purchase flow; a `revenuecat-webhook` Edge Function (per `CLAUDE.md`, not in local repo) keeps `profiles.is_premium` in sync. This is a fully separate system from the business-billing row above — no shared infrastructure. |
| Location | Yes | Yes (privacy-preserving by design) | `expo-location`, `presence_reports`/`sightings` tables | No client, anywhere in the app, ever receives another person's precise coordinates — enforced structurally (`profiles` has no lat/lng column at all), not just by convention. |
| Maps | Yes | Yes | `GatheringsMapView.js`, `react-native-maps` | Gathering markers (fuzzed unless the viewer is host/approved-attendee via a narrow RPC exception), business markers, "live now" highlighting. No people/community layer, deliberately (no real coordinate exists to plot for either). |
| Safety/reporting | Yes | Yes | `ReportBlockModal.js`, `reports` table, `date_checkins`, `EmergencyContactsScreen.js` | Includes a real date-safety check-in/share-location flow, admin report review, and persistent emergency contacts. No automated third-party alerting (no SMS/email infra exists in this codebase — deliberately not faked, per `CLAUDE.md`). |
| Blocking | Yes | Yes (with a documented historical bug now reportedly fixed) | `blocks` table, `is_blocked()` function | Per `CLAUDE.md`, this function was previously *not* `SECURITY DEFINER`, meaning a blocked user could still see/message the person who blocked them — described as fixed, but this audit did not independently re-run that live test to confirm the fix holds today; flagged for re-verification given severity. |
| Privacy | Yes | Mostly, with one explicit trade-off | RLS across most tables; `gatherings`/`communities` RLS is deliberately wide-open (app-layer gating only) | A real, repeated, explicit design choice in this schema (not an oversight) — see `PRODUCT_RISKS.md` for the implication of a direct/scripted client bypassing app-layer visibility rules. |
| AI features | Yes | Partial | `create-assistant` + `ai-concierge` Edge Functions, `RehearsalRoomScreen.js`, several `generate-*` functions referenced in `CLAUDE.md` | Real Anthropic calls exist and are deployed (per `CLAUDE.md`'s own account, independently corroborated by this repo's two local Edge Function source files that do have real content, unlike the other 4 empty stubs) — but end-to-end success of the actual model call was never exercised in *any* documented session (no way to mint a real signed-in session in a sandboxed environment) — treat the "does it actually return good results" question as unverified, not proven. |
| Premium features | Yes | Yes | `PaywallScreen.js`, gated checks across `noticeLimits.js`/`waveLimit`/`browseLimits.js`/`gatheringLimits.js`/`voiceNoteLimits.js`, `ai-concierge` | Per `CLAUDE.md`, these five daily-limit checks were previously bypassable via a spoofed local premium flag and were fixed to verify server-side — again, not independently re-tested in this pass. |
| Analytics (product/user-facing) | Yes | Yes | `InsightsScreen.js`, `MomentumScreen.js`, consistently "no fabricated numbers" per repeated project convention | All three read real, derived signals — no invented composite scores anywhere observed. Both are dead-end screens with no outbound action. |
| Analytics (business-facing) | Yes | Yes | `BusinessDashboardScreen.js`'s stats/growth/insights RPCs | Real aggregate data; per `CLAUDE.md`, these RPCs previously had **no ownership check** (any authenticated user could query another business's follower/redemption/top-member PII by guessing a `partner_id`) and were reportedly fixed — not independently re-verified live in this pass. |
| Analytics (operator/telemetry) | Yes | Yes | PostHog (`App.js`), Sentry (`App.js`) | Both wired with hardcoded client keys directly in `App.js` — normal for these SDKs (they're public client keys), but worth knowing they're not environment-configured. |
